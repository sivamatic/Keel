Keel-Pro: the story so far

Keel-Pro is a bigger, optional Keel model that runs on a GPU. This page shows what we built, how we test it and where it stands, mostly in pictures. Every number comes from a real run on our RTX 5090.

The goal in one line#

Score at least 62 on the Decision Index (DI) public index, the open benchmark for decision models, which puts Keel-Pro above Jev 1.14 (60.70).

Where that sits on the live board. The DI board (0.4.1, 346 entries, data of 2026-11-21) ranks models on a Full score from private tests that only its maintainers run. Keel-Pro has not been submitted yet. On the public index alone, 62.73 would place about #99; the best entries score 73–75. Microsoft-Decision-1 is not on the board. All 139,677 answers are public so anyone can re-score them: neerumsr/keel-pro-di-results.

How it works, end to end#

StepIn plain wordsWhere
1. DataWe collect practice questions from public training sets and write our own generators. We never train on DI's test questions.artifacts/parity/pro/DATA.md
2. TrainWe teach a small add-on (a "LoRA") on top of an open Qwen3.5 model. The base model stays untouched.training/pro/train_lora.py
3. ScoreWe ask the model 1,633 DI questions (the "dev" sample) and grade it with DI's own scoring code.scripts/di/eval_model.py
4. DecideBelow 62? Change one thing and train again. At 62 or above? That model is the finalist.artifacts/parity/pro/train-notes.md
5. ReportThe finalist answers a separate set of 3,272 questions, once, so the final number is not tuned.artifacts/parity/pro/di-results.md
6. ExportWe pack the model into GGUF files that run in llama.cpp, and check they give the same answers.scripts/di/gguf_check.py
7. ServeKeel sends a question to Keel-Pro only when the request asks for the decider-pro-1.0.0 model.artifacts/parity/pro/SERVE.md
8. PublishModel card and upload kit are ready. Nothing goes public without your OK.hf/keel-pro/, RELEASE_CHECKLIST.md

How Keel-Pro answers a question#

The model reads the situation and the options once. Each option gets a letter, and we read how likely the model thinks each letter is. It never writes free text, so it cannot ramble or invent an option.

Results#

  • Training lifts a stock model from about 10 to 60+.
  • The biggest single jump came from a bigger base model: 9B → 27B gave +6 points.
  • Averaging two 27B runs (soup78) gave the best dev score, 62.06.
  • On the separate report sample, scored once, the finalist gets 61.96 (95% range 58.98–64.42). Jev's 60.70 is inside that range, so we call it on par with Jev.
  • On the whole public suite (139,677 questions, all answered), it scores 62.73, above Jev's 60.70. HLE is still counted as 0, so the true number is a bit higher. About 98 board entries score higher on the public index.

Our 95% range (58.98–64.42) includes Jev. Plain reading: on par with Jev, mid-board overall, not a proven win.

Why it8 looks lower but is not simply worse. Music chords went from 2% to 85% right. But one sarcasm benchmark has a single "yes" example in our test sample: it7 caught it, it8 did not. That one tweet moves the whole index by ~1.7 points. Small samples are noisy, so we average both models.

The memory fix that unlocked it8, in plain words#

The longest questions (music chord charts, ~5,000 words) did not fit. The model kept one giant "who-looks-at-whom" table in memory for every question: its size grows with the length × the length. We switched to the slimmer method that builds the table in pieces.

Peak GPU memory, 5,000-token question
Before29.9 GB (over our limit, skipped)
After23.4 GB (fits)

Whole public suite (139,677 requests, fast engine, RTX 5090): median 245 ms, 80th percentile 438 ms, mean 528 ms, all under the 1 s limit ✅. 90% of requests finish within 1 s; the slowest 5% take over 1.27 s.

The GGUF builds also reuse the shared text (llama.cpp prompt cache), but answer the questions one at a time (about 140 ms each). So for many-question requests they are slower (ContractNLI 7.7 s); they are best for single questions. The CPU builds are for offline use. Both GGUF files pick the same answer as the scored model on 30 of 30 checked questions.

Honesty rules we follow#

  • Numbers come only from real runs. Vendor numbers are labelled.
  • The "report" sample is scored once, for the finalist only, so the result is not tuned to it.
  • We never train on DI test questions, and we never edit a test case to improve a score.
  • DI's HLE benchmark needs a gated download, so we score it as 0. That costs about 1.2 points on every row above.
